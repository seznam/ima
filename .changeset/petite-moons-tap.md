Add RTL-backed integration testing utilities to `@ima/testing-library`.

- **What?** Add the `@ima/testing-library/integration` entry point with `initImaApp`, `routeImaApp`, and `clearImaApp`. Integration boot loads the mapped `app/main`, renders and updates IMA page views inside React Testing Library's `act`, supports shared hooks under `setImaTestingLibraryClientConfig({ integration })`, and restores React roots, browser shims, timers, animation frames, assertions, and object-container state during cleanup. The boot sequence follows `reviveClientApp`: `onLoad` runs before the application is created and the `$Debug` global is derived from `$IMA.$Debug`. `initImaApp` boots without navigating and without starting the router listeners; `routeImaApp` sets the address bar and delegates to IMA's own `routeClientApp`, so listener setup, path extraction and fatal error handling stay in the framework. Global timers and animation frames are wrapped when the application boots, so Jest fake timers installed by the test are wrapped instead of replaced. Listener cleanup only removes registrations owned by the application's `$Window` service, preserving React's document listeners across boots. The application renderer owns its React root instead of registering it with RTL's global `render` registry, so teardown releases the root without cleaning up unrelated RTL renders, and restores the original server markup. Overlapping cleanup calls are queued so the next application cannot boot against partially destroyed state. `setImaTestingLibraryServerConfig({ environment })` defaults to `test` for both unit and integration tests and is passed explicitly to `createIMAServer` without modifying process variables. Environment processors receive and return `ParsedEnvironment`, and the template's SPA override preserves the other normalized degradation callbacks. New `create-ima-app` projects use the shared integration utilities.
- **Why?** Integration tests can reuse the JSDOM initialized by the existing Jest preset and consistently select their configured IMA environment instead of depending on `NODE_ENV` or module import order. Deferring navigation to `routeClientApp` keeps the tested boot sequence aligned with the application sources instead of reimplementing it, which removes the need to patch `ClientRouter` through `to-aop`. Environment overrides must preserve normalized settings.
- **How?** Upgrade to `@ima/testing-library` 21 and install `@ima/server` 20.1 or newer. Replace `@ima/plugin-testing-integration` imports with `@ima/testing-library/integration`, configure server-time values through `@ima/testing-library/server`, and move runtime hooks to the `integration` key of `setImaTestingLibraryClientConfig`. Replace the initial `app.oc.get('$Router').route(path)` call with `routeImaApp(app, path)`; `initImaApp` no longer starts the router listeners on its own. `initRoutes` overrides run in addition to the application's routes, so they can only add routes. Existing unit and integration suites that selected their environment through `IMA_ENV` or `NODE_ENV` must explicitly configure their previous environment; use `setImaTestingLibraryServerConfig({ environment: undefined })` only to retain legacy shell-based resolution. Return all normalized settings from `processEnvironment` callbacks, preserving existing fields when overriding values. Use `$Window.bindEventListener` for application-owned listeners; remove directly registered native listeners in their owner's teardown. Awaiting `clearImaApp` is recommended, but not required, because the next `initImaApp` waits for pending cleanup.
